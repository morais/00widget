# Agent guide — 00Widget

Operational notes for agents (and humans) working on this repo.

## What this is

A reusable iOS companion app and Cloudflare Worker backend that lets any agent publish structured state (cards + Live Activities + actions) to iOS widgets, the Lock Screen, and the Dynamic Island.

The server **never** sends UI. It sends typed JSON state matching the templates in the data model; the iOS app/widget renders it through predefined SwiftUI views. New use-cases (solar, washer, school balances, car charging, etc.) should be expressible by *publishing the right state*, not by adding code.

## Layout

```
ios/        SwiftUI app + WidgetKit extension + Live Activity (iOS 26+, generated by XcodeGen)
server/     Cloudflare Worker, TypeScript, D1-backed (per-API-key isolation via sha256 hash)
examples/   curl scripts demonstrating the public API
```

The data model is duplicated by design:

- Swift source of truth: `ios/Sources/Shared/Models/`
- TypeScript zod schemas: `server/src/types.ts`

**Keep the two in lockstep.** Adding a field to `DashboardCard` means editing both files in the same change.

## Secrets and open-source hygiene

This repo is intended to be public. **Never commit secrets.**

Always gitignored:
- `examples/env.sh` (real `BASE_URL` + `API_KEY`)
- `server/.dev.vars` (Wrangler local secrets, including `APNS_PRIVATE_KEY`)
- `*.p8`, `*.pem` (APNs private keys)
- `ios/*.xcodeproj/` (XcodeGen output)
- `ios/Resources/*/Info.plist` and `*.entitlements` (XcodeGen writes these from `project.yml`)
- `node_modules/`, `.wrangler/`, `build/`, `DerivedData/`, `.env`

### Per-developer config — `.sample` template pattern

Two files would otherwise go dirty in every developer's working tree because they hold per-developer values (D1 ids, Apple Developer Team ID, real bundle ids, App Group). They're **gitignored**, with a committed `.sample` sibling acting as the source-of-truth:

| Gitignored real file       | Committed template            |
| -------------------------- | ----------------------------- |
| `server/wrangler.toml`     | `server/wrangler.toml.sample` |
| `ios/project.yml`          | `ios/project.yml.sample`      |

First-time setup is `cp <name>.sample <name>` and then edit. If you change anything that should apply to everyone (route paths, target structure, etc.), edit the `.sample` and copy it forward.

The App Group identifier is consumed by both targets' Info.plists and entitlements, but you only edit `project.yml` — both targets receive `ZWAppGroupIdentifier` from `project.yml`'s `info.properties`, and `Constants.swift` reads it at runtime via `Bundle.main.object(forInfoDictionaryKey: "ZWAppGroupIdentifier")` with the `group.com.example.zerozerowidget` placeholder as fallback. The shared Keychain access group is also configured in `project.yml` so widget App Intents can read the API key. **Don't reintroduce hardcoded App Group or Keychain group strings in Swift.**

Placeholder values that must stay in committed `.sample` files (and source code fallbacks):
- Bundle id: `com.example.zerozerowidget`
- App Group: `group.com.example.zerozerowidget`
- Wrangler `[[d1_databases]] database_id`: `REPLACE_WITH_D1_DATABASE_ID`

## Simulator builds without an Apple Developer team

Use `ios/scripts/build-sim.sh` rather than rolling your own `xcodebuild` invocation. The script bakes in three lessons that cost real time the first time around:

- **`CODE_SIGNING_ALLOWED=NO` skips entitlements embedding entirely.** The app launches, but the App Group container is unavailable at runtime — `CardCache.save` throws "App Group container unavailable" and nothing survives a relaunch. Symptoms: Test Backend Connection works (no auth needed), but the Dashboard never populates and the Debug tab shows that exact error.
- **Ad-hoc signing alone (`CODE_SIGN_IDENTITY="-"`) doesn't get xcodebuild to embed entitlements either.** The `.app` bundle's entitlements come back as `[Dict]` with no keys.
- **Re-signing with the production `.entitlements` is rejected at launch** — `SBMainWorkspace` denies the launch because `aps-environment` can't be satisfied without a real provisioning profile. Drop `aps-environment` for sim runs; push doesn't work on sim out of the box anyway.

The script's recipe: build with ad-hoc signing → re-sign the app and the widget extension with an App-Group-only entitlements file → install → optionally seed the server URL into UserDefaults via PlistBuddy. The API key still has to be pasted manually because it lives in Keychain.

During iterative simulator work, prefer `ios/scripts/build-sim.sh --launch` so existing app data, Keychain values, notification permissions, and local settings survive. Use `--fresh` only when intentionally testing first-install behavior or reset/migration paths, because it uninstalls the app and makes iOS ask for permissions again.

When working on a real device with a configured Team ID, none of this applies — Xcode handles signing/entitlements via the project settings.

## Widget configuration cannot be verified on the Simulator

Picking a card for a `CardWidget` works on device and **does not work on the
iOS Simulator**. The extension's `entry(for:)` always receives the first cached
card, and `CardEntityQuery.entities(for:)` is never called at all — AppIntents
does not invoke the query to rehydrate the widget's stored entity there. The
configuration itself is fine: the picker shows the chosen card ticked, and the
same build installed from TestFlight behaves correctly.

Ruled out, each by direct test, before concluding it is the runtime: the commit
history (reproduces on a commit that shipped working to TestFlight), simulator
state (reproduces on `simctl erase`), the intent living in `Sources/Widgets`
rather than `Sources/Shared`, the stripped ad-hoc entitlements from
`build-sim.sh` (re-signed with team identifier, `application-identifier` and
`keychain-access-groups`), and Debug vs Release.

Verify widget configuration on a device. Do not spend time on it in the
Simulator.

Note also that `build-sim.sh --fresh` only runs `simctl uninstall`, which leaves
the **shared App Group container** intact — cached cards and widget placements
survive it. Use `xcrun simctl erase` for a genuinely clean device.

## Marketing screenshots

`ios/scripts/capture-screenshots.sh` drives the app with XCUITest
(`ios/UITests/ScreenshotTests.swift`) and writes PNGs to
`ios/build/screenshots/`. To publish the canonical iPhone set, pass the
destination asset directory explicitly; the repository location is never
assumed:

```
ios/scripts/copy-screenshots.sh --to /path/to/site/public/assets
ios/scripts/copy-screenshots.sh --only activities --to /path/to/site/public/assets
ios/scripts/copy-screenshots.sh --set ipad --to /path/to/site/public/assets/ipad
ios/scripts/copy-screenshots.sh --set tvos --to /path/to/site/public/assets/tvos
ios/scripts/copy-screenshots.sh --set tvos --only activities --to /path/to/site/public/assets/tvos
```

For a quick Activities-only refresh, use
`ios/scripts/capture-screenshots.sh --only activities` (and add `--device` for
iPad). This skips Home Screen widget placement while producing the same
`screenshot-activities.png` filename consumed by the copy helper.

The iOS and tvOS capture scripts reuse incremental DerivedData under
`ios/build/ScreenshotDerivedData-*`. Leave those gitignored caches in place
during iteration; delete one only when intentionally diagnosing a clean-build
problem. Screenshot-only widget configurations are listed first in the private
widget bundle so XCUITest traverses fewer picker pages. Shipping bundle order is
unchanged because those configurations compile only with `ZW_SCREENSHOTS`.

Apple TV uses `ios/scripts/capture-tv-screenshots.sh`, which builds a private
`ZW_SCREENSHOTS` sample dashboard through the dedicated
`ZeroZeroWidgetTVScreenshots` scheme and writes native 1920×1080 PNGs to
`ios/build/screenshots/tvos/`. The screenshot-only state and UI-test target are
not compiled into the shipping tvOS scheme. A full run captures the general
dashboard, the Energy/Deploys/Device fleet insights dashboard with a running
Live Activity, and the Live Activity dashboard. Pass `--only activities` for a
quick Activities-only refresh.

A UI test is the only way in. The simulator cannot be driven from outside: the
app opens on Settings until an API key is in the **Keychain**, which cannot be
seeded externally; `onOpenURL` forwards external links rather than routing tabs;
and there is no tap tooling — `simctl` has no tap verb and the Simulator exposes
no accessibility windows to AppleScript. XCUITest runs on-device and can tap.

The script does **not** run a plain `xcodebuild test`. It builds with
`build-for-testing`, re-signs the app and the widget extension with App-Group
entitlements the way `build-sim.sh` does, then runs `test-without-building`
against the re-signed products. That middle step is load-bearing:
`CODE_SIGNING_ALLOWED=NO` embeds no entitlements and leaves the App Group
container unavailable. The app tolerates that — `CardCache.save` is a `try?`, so
cards fall back to memory — but the widget extension is a **separate process**
with no such fallback, so every Home Screen widget renders empty. Re-signing
gives both processes the container. Verified: widgets show real cards, and
`test-without-building` installs the re-signed bundle rather than rebuilding it.

**Sample data is labelled** with a "these are samples" notice and `SAMPLE`
badges. The run suppresses that through Settings → Developer → "Hide sample
indicators", which the UI test toggles on. The flag is off by default and lives
in the App Group, which is the other reason the re-signing matters — without the
container the extension cannot read the flag and widgets keep their badges.

The Developer section itself is gated on the `ZW_DEBUG_TOOLS` build setting,
which is `NO` everywhere. `capture-screenshots.sh` passes
`ZW_DEBUG_TOOLS=YES`, so no shipping build contains the screen or any way to
reach the flag. `Constants.debugToolsEnabled` accepts a Bool or a `YES`/`NO`
string, because a value substituted from a build setting arrives as a string,
and fails closed on anything else.

XCUITest can drive Springboard (`XCUIApplication(bundleIdentifier:
"com.apple.springboard")`), which is how the expanded Dynamic Island is
captured — a long-press on the island after backgrounding the app. The same test
also rebuilds the dedicated marketing Home Screen page twice on every run. The
classic capture has three small Solar, Washer, and Boiler widgets plus a wide
Energy chart; the insights capture uses small Energy, Deploys, and Device fleet
widgets. It removes any previous 00Widget layout, adds each set through
SpringBoard's widget gallery, and asserts the expected sizes exist before capturing
`screenshot-home-widgets.png` and `screenshot-home-insights.png`.

Pass `--device "iPad Pro 13-inch (M4)"` to capture the App Store iPad set under
`ios/build/screenshots/ipad/`. It produces native 2064×2752 images, uses the
same two layouts on a clean regular Home Screen page, and captures
the Widgets, insights, breakdown, and Activities app surfaces. The run turns
off both optional iPad dock sections through Settings; otherwise the App
Library button previews the installed UI-test runner as an apparent extra
00Widget icon. It intentionally omits the compact and expanded Dynamic Island
variants, because iPad has no Dynamic Island.

The screenshot script builds with the private `ZW_SCREENSHOTS` compilation
condition. It adds static widget kinds that feed Solar, Washer, Boiler, Energy,
Deploys, and Device fleet through the production card renderer, including a
medium Energy variant for the classic layout. The latter three small variants
power the chart-focused Home Screen capture. This is necessary
because the Simulator does not rehydrate stored AppIntent card selections (see
"Widget configuration cannot be verified on the Simulator" above), so three
normal configurable widgets cannot retain three distinct cards there. Ordinary
simulator builds and every shipping build do not compile these widget kinds.

### Schemes are declared explicitly

`project.yml` declares `ZeroZeroWidgetApp`, `ZeroZeroWidgetTV`,
`ZeroZeroWidgetTests`, `ZeroZeroWidgetScreenshots`, and
`ZeroZeroWidgetTVScreenshots`. This is
load-bearing: adding *any* `schemes:` entry
turns off Xcode's scheme autocreation for every target, which silently removed
the `ZeroZeroWidgetApp` scheme that `build-sim.sh` and `upload-testflight.sh`
archive with. If you add a target, add its scheme too. Every test target — the
two UI test bundles and the unit test bundle — is reachable only from its own
scheme, never from `ZeroZeroWidgetApp`, so none of them can enter an archive.

## TestFlight submissions

Use `ios/scripts/upload-testflight.sh`. It bumps the build number, regenerates
the project, archives both platforms, runs the release gates below, and uploads.
Do not hand-roll the `xcodebuild` invocations — the gates exist because each one
corresponds to a way a build has already reached TestFlight broken.

```
ios/scripts/upload-testflight.sh                # both platforms
ios/scripts/upload-testflight.sh --ios-only
ios/scripts/upload-testflight.sh --verify-only  # archive + gates, no upload
```

Credentials live outside every checkout and are never read from the repo:

| What | Where | Override |
| ---- | ----- | -------- |
| API key | `~/.appstoreconnect/private_keys/AuthKey_<KEYID>.p8` | `ASC_KEY_PATH`, `ASC_KEY_ID` |
| Issuer ID | `~/.appstoreconnect/issuer_id` | `ASC_ISSUER_ID` |

Both should be `chmod 600`. The Issuer ID comes from App Store Connect →
Users and Access → Integrations → App Store Connect API. Team ID and bundle ids
are read from your gitignored `ios/project.yml`, so nothing identifying is
committed.

### The gates, and why each exists

1. **Build number reaches every plist.** `CURRENT_PROJECT_VERSION` is bumped to
   a `YYYYMMDDHHMM` timestamp, then asserted in the generated Info.plists and
   again in the archive, app, and widget extension. A mis-set `project.yml`
   silently yields a literal `1`, and App Store Connect only rejects it *after*
   a full archive. `MARKETING_VERSION` stays put unless a version bump is asked
   for.
2. **`aps-environment` is `production` in the signed iOS app.** The archive
   reads `development` even for Release builds — that is expected, not a bug.
   The export step re-signs with the distribution profile and flips it. Only the
   exported IPA tells you what TestFlight receives, so never "verify" the
   archive and conclude anything.
3. **`com.apple.developer.applesignin` survives into the signed tvOS app.** A
   profile can grant the capability while the final signature omits it, in which
   case Sign in with Apple fails at runtime on a build that installed fine.
4. **`com.apple.developer.associated-domains` survives into the signed iOS
   app.** Same trap as gate 3 and a quieter one: a dropped entitlement has no
   symptom beyond universal links continuing to open in Safari, and Apple's CDN
   caches the wrong association for hours afterwards. Each platform takes a
   `;`-separated list of entitlements, and a run reports every missing one
   rather than stopping at the first.
5. **The signed widget extension has production APNs.** WidgetKit push belongs
   to the separately signed `ZeroZeroWidgetWidgets.appex`; a production
   entitlement on the containing app does not prove the extension kept one.
   The exported IPA must show `aps-environment` as `production` on the appex or
   WidgetKit pushes can leave the server looking healthy while no timeline runs.

### Keeping iOS and tvOS symmetric

Both platforms run through one function in the script; their differences are
arguments, not branches. Preserve that — a platform fix belongs in the call
site, not in a new conditional.

Both platforms archive under **automatic signing with no configuration** — no
profile overrides, no env vars. If you hit an asymmetry, it is almost certainly
**account state, not project structure**, and the fix belongs in the developer
portal rather than in this script.

The one that has actually happened: automatic signing archives against a
*development* profile, and Apple mints one only for a platform that has a
registered device. A team with registered iPhones and no Apple TV can archive
iOS and not tvOS, failing with:

```
Your team has no devices from which to generate a provisioning profile.
No profiles for '<bundle id>' were found: Xcode couldn't find any tvOS App
Development provisioning profiles matching '<bundle id>'.
```

Register the device and it goes away. Get the UDID by pairing the Apple TV to
Xcode over the network (Apple TV: Settings → Remotes and Devices → Remote App
and Devices; then Xcode → Window → Devices and Simulators → Pair). Xcode prints
`Identifier: <UDID> (<other id>)` — **register the first value**, the
25-character `8hex-16hex` form. The parenthesised RFC-4122 UUID is a different
identifier and the Devices portal rejects it.

Two things that do *not* work, both confirmed the hard way:

- Passing App Store Connect credentials to `xcodebuild archive`. They reach
  Apple, and Apple still declines to mint a development profile for a platform
  with no registered devices.
- Signing manually with an Xcode-managed profile. Manual signing rejects them;
  it needs one you created yourself in the portal.

`ZW_TVOS_PROFILE` / `ZW_IOS_PROFILE` remain as an escape hatch for a machine
that genuinely cannot register a device — point them at a manually managed App
Store profile. Prefer registering the device; it removes the special case
instead of papering over it.

The tvOS target intentionally shares the iOS app's bundle identifier so both
attach to the same multi-platform App Store Connect record. Keep the real
identifier only in the gitignored `ios/project.yml`; keep placeholders in
`ios/project.yml.sample`.

### If you must do it by hand

Reach for this only when debugging the script itself. Archive with
`xcodebuild archive -project ZeroZeroWidget.xcodeproj -scheme
ZeroZeroWidgetApp -configuration Release -destination 'generic/platform=iOS'
-archivePath <path>` (swap in `ZeroZeroWidgetTV` and
`generic/platform=tvOS` for Apple TV), then export with an options plist using
`method: app-store-connect` and `manageAppVersionAndBuildNumber: false`, written
under `/tmp` and never in the repo. Export to a local directory first and check
the resulting IPA:

```
codesign -d --entitlements - --xml <app> | plutil -p -
```

Then re-export with `destination: upload`. Success looks like
`Uploaded package is processing` followed by `Upload succeeded`. If the failure
says the bundle version must be higher than a previous upload, the archive still
holds the wrong `CFBundleVersion` — fix the generated plist inputs and
re-archive rather than retrying the same archive.

## Turning subscriptions on

Everything below is off in every committed configuration. Enabling it is four
separate steps and partially doing it is worse than not starting: a build with
`ZW_SUBSCRIPTIONS_ENABLED` and a server that sells nothing shows an empty
paywall, and a server with `SUBSCRIPTION_REQUIRED` and no way to buy locks every
producer out.

1. **App Store Connect.** Create one subscription group with two products,
   monthly and yearly. Same group, or upgrading and downgrading will not
   prorate. Add the free trial as an *introductory offer on the group* — the
   server needs no trial special case, because a trial is an entitlement with an
   expiry like any other. Turn on the billing grace period while you are there;
   it arrives in the renewal info and is honoured.
2. **Notifications.** Point App Store Server Notifications V2 at
   `https://<host>/v1/apple/subscription-notifications`, production *and*
   sandbox. Skipping this leaves the stored entitlement wrong for everything
   that happens while the app is closed.
3. **Server.** Set `SUBSCRIPTIONS_ENABLED`, `SUBSCRIPTION_PRODUCT_IDS`, and
   `SUBSCRIPTION_ENVIRONMENT`. Leave `SUBSCRIPTION_REQUIRED` off until the
   entitlement data looks right — that is what the two flags are for. Before
   turning it on, decide about existing tenants; grandfathering is a one-off
   insert of non-expiring rows and is easiest while nothing is enforced.
4. **App.** Add `ZW_SUBSCRIPTIONS_ENABLED` to
   `SWIFT_ACTIVE_COMPILATION_CONDITIONS` in your `project.yml` and rerun
   `xcodegen`. Test purchases against `ios/Resources/ZeroZeroWidget.storekit` in
   the Simulator and the real trial and renewal flows with a Sandbox account on
   a device.

Two things not built, in case they look missing rather than declined. There is
no App Store Server API polling — it needs a second `.p8` and reconciles what
notifications plus client verification already cover. And Family Sharing is off:
enabling it on the products breaks the one-purchase-one-tenant rule by design,
so decide what that should mean before turning it on.

## Things to watch

- **APNs payload shapes are date-stamped in `server/src/apns.ts`.** Apple has shifted ActivityKit / WidgetKit payload field names and header values across iOS releases. Before changing those helpers, re-check the live docs:
  - https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications
  - https://developer.apple.com/documentation/WidgetKit/Updating-widgets-with-widgetkit-push-notifications
- **A Live Activity's `title`, `kind`, and `deepLink` are `ActivityAttributes`, frozen at start.** Only `ContentState` travels in an update push, so `/v1/live-activities/update` can persist a new `title` to D1 (and to `GET /v1/live-activities`) while the Lock Screen keeps the original forever. `EndLiveActivitySchema` deliberately has no `finalTitle` for the same reason. Anything a producer expects to change must live in `ContentState` — see the "`title` is frozen" section of `docs/llms.md` before moving a field across that line.
- **D1 bills index maintenance as rows written, and rows written cost 1000× rows read.** An index on a column an `ON CONFLICT` path updates doubles the price of that write. This is why `rate_limit_buckets` — the hottest write in the system, hit several times per authenticated request — deliberately carries no index on `expires_at`, and why its expiry sweep runs off the request path entirely, sampled on the widget-reload queue consumer under `waitUntil` because the account has no spare cron trigger. That sweep deletes in bounded chunks by `rowid` rather than scanning on `expires_at`, so one call costs the same however far behind the table has fallen. Before adding an index to a table on a write path, work out what it does to rows written, not just to read latency.
- **The Apple Sign-In return URL is `/auth/apple/callback`.** It is registered in the Services ID at developer.apple.com *and* set as `APPLE_SIGN_IN_REDIRECT_URI`; the two must match exactly or sign-in fails with a redirect_uri mismatch from Apple, before any of this code runs. Moving that path again means a portal edit, so don't do it casually.
- **Associated domains are configured in two places that must agree.** The Worker serves `/.well-known/apple-app-site-association` from the `APPLE_APP_ID` var in the gitignored `wrangler.toml` (`<Team ID>.<bundle id>`), and the iOS app claims the host in its `com.apple.developer.associated-domains` entitlement in the gitignored `project.yml`. A mismatch fails silently in both directions — links simply keep opening in Safari, with no error on the device or in the Worker logs. The app claims only the `/app/*` prefix (`UNIVERSAL_LINK_PATH_PREFIX` in `server/src/appleAppSite.ts`, mirrored by `ZeroZeroWidgetUniversalLink.pathPrefix`); widening it to `*` would swallow `/admin/*`, which is a web sign-in flow that breaks when iOS diverts it into the app. Apple's CDN caches the association, so append `?mode=developer` to the entitlement while testing an unreleased change — and take it back out before release.
- **App Group and shared Keychain identifiers come from `project.yml`.** The generated Info.plists and entitlements must match across the app and widget targets; edit `project.yml.sample` for shared changes and rerun `xcodegen`.
- **The iOS app never holds the APNs `.p8`.** Only the backend has it, as a Wrangler secret. Don't introduce code that reads APNs private material on-device.
- **Destructive actions don't run from widgets.** `RunDashboardActionIntent` checks `ActionDefinition.isSafeFromWidget` and silently no-ops for `role == .destructive` or `confirm == true`. Route those to the app via `deepLink` instead — don't loosen this without explicit user signoff.
- **Guest links are view-only and bound to one resource id.** A `zwg_` credential carries only the `guest:read` scope, which no other route accepts, so the existing scope check is the whole enforcement — don't add `guest:read` to another route, and don't widen the guest preset. Cards come back with `actions` stripped. Links are bound to a resource *id*, never a resource kind: binding by kind is the sharp edge that made `SHARING_ENABLED` default to off, since a share for kind `progress` exposes every current and future progress activity. They are `api_keys` rows carrying the minting session's `session_id` so sign-out revokes them for free, and they never renew on use, because sliding expiry on a credential printed on a QR code would let anyone holding it keep it alive indefinitely.
- **A guest link's token lives in the URL fragment** (`/app/g#<token>`), never the path, so it is never sent to the Worker and never reaches Cloudflare's request logs. `server/test/guestLinks.test.ts` pins the URL shape; if you change how links are built, keep the `#`.
- **D1 tenant isolation and scopes.** Every app/agent token is stored hashed in `api_keys`, maps to a `tenant_id`, and has explicit capability scopes; tenants store `owner_email` for ops/account ownership, and storage tables use `tenant_id` in their primary keys. New `/v1/*` routes must use `authed(...)` with a required scope and scope queries through `auth.tenantId`.
- **An MCP tool's `outputSchema` and its handler's response must stay in lockstep, and nothing on the server checks.** `structuredContent` is the route's own JSON passed through untouched — no layer validates it against the schema the tool advertised. Zod converts a plain object with `additionalProperties: false`, so a single field the handler returns and the schema omits makes a strict client reject the whole response; the tool goes dark with no error in the logs and a 200 in the metrics. `get_status` shipped that way for three days after the delivery-diagnostics change added two fields to `status.ts` and none to `mcp.ts`. Tests that assert every declared field is present cannot catch it — that is the other direction. `test/mcp.test.ts` now calls every tool and compares what comes back against what it advertised, both ways; keep new tools inside that sweep rather than testing their shape by hand.
- **The MCP endpoint is an adapter, not a second API.** Each tool in `server/src/mcp.ts` builds the request its `/v1` route would have received and calls the same handler, with the same zod schema converted to JSON Schema at startup. Never reimplement a rule (validation, rate limit, reload coalescing) inside a tool — if a tool needs different behavior, the handler is the wrong shape.
- **A web session is identity; admin is a capability on top of it.** `/login` authenticates anyone who already has an account, and `ADMIN_EMAILS` decides only whether that session carries `isAdmin`. Every `/admin` route asserts the capability explicitly — never infer it from a session existing, and never gate authentication on `ADMIN_EMAILS` again, which is what made every web surface an admin surface by construction. The capability is evaluated when the session is read, so rotating `ADMIN_EMAILS` applies on the next request.
- **Signing in never signs anyone up.** `resolveIdentity` reads; it does not create. Accounts are born in the iOS app (`appLogin.ts`), and web sign-in turns away an Apple identity it cannot resolve unless `WEB_SIGNUP_ENABLED` is `"true"`. If you add another way to authenticate, it inherits this rule: a new tenant is a deliberate, gated act, not a side effect of a successful login.
- **A handler re-resolves what an identity may touch; it never takes it from the request.** The MCP consent screen is the live example — the tenant a connector is bound to comes from the signed-in identity at approval time, not from the form, so a planted `tenantId` cannot redirect a credential to someone else's account.
- **ChatGPT speaks the 2026-07-28 MCP revision, and its shapes are exact.** `openai-mcp/1.0.0` opens with an empty `POST /mcp` probe, then `server/discover`, then `tools/list`, then `tools/call`. A `DiscoverResult` returns `supportedVersions` (a *list*), `capabilities`, and `serverInfo` under `_meta["io.modelcontextprotocol/serverInfo"]` — not the legacy handshake's single `protocolVersion` with a top-level `serverInfo`. Getting that wrong makes the result unparseable, and the client silently stops there: no tools, no error you can see, and a connector that reports itself installed while exposing nothing. Check a response against the schema page for the revision the client declares, not against a summary of it.
- **A scope name is stored data, not just an identifier.** `api_keys.scopes_json` holds the literal strings, and every credential already issued carries the spelling it was minted with — including the three the iOS app creates on each sign-in. So renaming one means adding it to `RENAMED_SCOPES` in `auth.ts`, which translates before the value is checked against `API_SCOPES`; that is what let `tenant:read` become `read` with no migration and no broken credential. The naming rule the set follows: a bare verb spans resources (`read`, `publish`, both covering cards and Live Activities), a prefix names the one thing the scope touches.
- **An MCP token publishes; it does not administer.** `ApiScopePresets.mcp` is the producer preset minus `webhook:manage`, and that subtraction is the whole design: a webhook is an HTTPS endpoint the operator runs plus a signing secret handed back exactly once, and neither belongs to a connector approved through a browser consent screen — which has nowhere to put a secret it is shown once. Cards published over MCP may still carry `actions`, and the buttons work, but only against a webhook registered with an API token by whatever owns the endpoint. Don't widen `GRANTABLE_SCOPES` back to `producer` to "make actions work over MCP"; the answer is the fuller integration. Tokens minted before this narrowing keep the scope they were issued with — revoke them in `/admin` if that matters.
- **Every MCP method requires a credential; only the empty probe does not.** ChatGPT authenticates `server/discover`, `tools/list` and `tools/call` alike. An earlier version served the tool list anonymously, on the mistaken reading that the unauthenticated requests in the logs were tool listings — they were the probe. Before loosening this again, log the *method*: `hasAuthorizationHeader` alone cannot tell you which request was unauthenticated.
- **An empty `POST /mcp` is a probe, not a request.** Answer 202. It carries no JSON-RPC message to authenticate or fail, and a 401 there tells a client to authenticate at a point in its flow where it holds no credential, sending it back around discovery forever.
- **MCP authorization is OAuth only because ChatGPT allows nothing else.** Its connectors can present an OAuth token or no credential at all — never a custom API key or header. Everything that flow produces is an ordinary `api_keys` row with the `mcp` preset, so `requireAuth` has no MCP special case; keep it that way. Registered clients and authorization codes are HMAC-signed values, not rows, which is why *issuing* needs no table — but redemption is recorded in `mcp_authorization_codes`, because a signed value cannot be marked used and every redemption mints a credential. Claim it with `INSERT OR IGNORE` on the `jti` so the check and the claim are one statement, and claim it **last**, after the client id, redirect URI and PKCE all check out: a failed exchange must not burn a code the legitimate client is still about to present correctly. A token in the URL path was ruled out for the same reason guest tokens live in the fragment: Cloudflare logs request paths.
- **Subscriptions are two flags, and both default off.** `SUBSCRIPTIONS_ENABLED` turns on verification and the App Store Server Notifications endpoint; `SUBSCRIPTION_REQUIRED` additionally gates writes. The middle state is the point — selling before enforcing, to grandfather existing tenants. `REQUIRED` without `ENABLED` fails **open** on purpose: a monetization switch that locks out paying customers on a typo is worse than one that bills nobody. On iOS the whole feature is behind `ZW_SUBSCRIPTIONS_ENABLED`, which no committed configuration sets, so the guarded code is not exercised by an ordinary build — **build both states before trusting a change to it**, and use a deliberate error inside the guard to confirm the flag is actually taking effect.
- **The subscription gate has two call sites because MCP does not use `authed`.** `server/src/mcp.ts` re-implements its own scope check and calls route handlers directly, so a gate placed only in the `authed` wrapper leaves the agent-facing half of the product — the half that publishes — completely ungated. Both call sites share `subscriptionGate`. Anything else added to `authed` as a cross-cutting rule inherits this trap.
- **Entitlement gates writes, never reads.** `publish` and `actions:run` only. A lapsed subscriber whose widgets go blank has a broken Lock Screen and no explanation; one whose widgets freeze at their last state understands. `device:register` stays open too, or renewing lands on a device the server cannot push to, and the `/v1/subscription/*` routes stay open or renewing is impossible.
- **`originalTransactionId` is an App Store account; `tenant_id` is a Sign in with Apple identity.** They usually coincide and are not required to, which is why `subscriptions` is keyed by the former with a nullable latter. A notification carries no identity, so it lands unclaimed and is adopted when the app next verifies; a purchase is never moved between tenants, or replaying one receipt under a second sign-in would entitle both.
- **Apple's signing chain is mixed-curve.** The leaf that signs a JWS is P-256/ES256, but the WWDR G6 intermediate and Apple Root CA - G3 above it are P-384 signing with `ecdsa-with-SHA384`. `appleJws.ts` reads curve and hash from each certificate; hardcoding P-256 makes every real payload fail with "Named curve mismatch" while every locally minted fixture still passes. Any test chain should reproduce the mixed shape.
- **A chain is signature linkage plus issuer authority, and the second half is the one that gets forgotten.** `verifyChain` pins the root by byte equality and verifies each certificate under the next one's key. That alone accepted any end-entity certificate under Apple Root CA - G3 as an intermediate — and Apple issues those to every Developer Program member, so an attacker signs a certificate for their own key with the one they legitimately hold, presents `[forged leaf, their real leaf, WWDR, root]`, and forges any transaction or notification for any bundle id. `parseCertificate` therefore reads `basicConstraints` and `keyUsage`, and every certificate between the leaf and the anchor must assert `cA`, satisfy its own `pathLenConstraint`, and assert `keyCertSign` where it states a `keyUsage` at all. An absent `basicConstraints` reads as `cA=FALSE`; treating a missing extension as permission is the same bug in a quieter form. The **trust anchor is deliberately exempt** — it is trusted by pinning, which is a stronger statement than its own extensions, and RFC 5280 §6.1 treats it the same way. Fixtures minted without extensions cannot see any of this, which is why `appleCertFixtures.ts` emits both.
- **An Apple signature proves who signed, never what it was signed about.** A notification's `signedTransactionInfo` and `signedRenewalInfo` are two independently signed payloads in one body that an unauthenticated caller composes, so each has to be checked to be about the same subscription: `applyRenewalInfo` requires the renewal info's own `originalTransactionId` to match, and re-checks bundle id, product and environment. Without that, renewal info Apple genuinely signed for another app carried a `gracePeriodExpiresDate` that `evaluateSubscription` reads as a reason to stay active. Its `UPDATE` also carries the `signedDate` guard `recordTransaction` has, because Apple does not guarantee ordering and the endpoint is open to replay. `FakeD1` matched that statement on a **prefix** and silently dropped the guard — see the `FakeD1` bullet above; it now matches the whole string so the next clause fails loudly.
- **A security check with nothing to check against must close, not vanish.** `if (expectedBundleId && bundleId !== expectedBundleId)` meant an unset `APNS_BUNDLE_ID` removed the check rather than failing it, and every transaction on the App Store verified. Subscriptions and APNs are configured independently, so that state is reachable. The pattern to copy is the environment check beside it, which defaults to `"Production"` and always applies — or `isSecureAdminSecret`, which closes web sign-in rather than opening it. `SUBSCRIPTION_PRODUCT_IDS` is the deliberate exception and says so where it is read.
- **Without the notification endpoint the stored entitlement is wrong.** Client-side verification only runs when the app is open. Cancellations, billing failures, and refunds all happen while it is closed, and for a renewal that failed the app may never open again. Both paths funnel into `recordTransaction`, whose `ON CONFLICT` never clears an existing `tenant_id` and never lets an older payload overwrite a newer one — Apple does not guarantee notification ordering.
- **Card upsert is unconditionally last-write-wins, and that is the documented contract.** There is no version, no `If-Unmodified-Since`, and no compare-and-set: the card in the request replaces the stored one whole, so two producers sharing an id silently overwrite each other and neither learns of it. The answer is namespaced ids, which the stable-id guidance already asks for. If a conditional write is ever wanted it has to arrive as an optional request field — changing what a plain upsert does would break every producer relying on the current behaviour.
- **`FakeD1` proves logic, not bindings.** It reads the bound array positionally, so a statement whose placeholders and values are misaligned passes the suite and fails against D1 — and a conditional upsert that wrongly returns false is silent, since "no rows changed" is a legitimate outcome rather than an error. The widget reload claim is the live example: it binds five values twelve times. Prefer plain `?` there over numbered `?NNN`, keep the bind order commented, and check a new statement of that shape against the real database rather than trusting a green suite. The rate limiter is the second: when its upsert grew a `weight`, the fake still read position 2 as `expires_at` and still added a hardcoded 1, so the change passed 448 tests while storing a weight in the expiry column and ignoring the weight entirely. When a statement's bind order changes, the fake's reader changes with it — and a helper that mirrors a real statement should say so in a comment.
- **A tenant-wide rate limit is derived, not counted.** `cardUpsertTenantHour` *is* the sum of that tenant's `cardUpsertCardHour` buckets in the window, so storing it too meant a second row write on every publish to record what the first row already contained — and rows written cost 1000x rows read. `DERIVED_TOTALS` in `rateLimit.ts` names each total and what it sums; the enforcement path writes only the buckets that are not derived and answers the rest with one range read that rides in the same batch, ordered last so it observes the write it just made. Two consequences to keep in mind. A route that names *only* derived buckets would be counted by nothing and limited by nothing — that is why `deleteCard` charges the card's own bucket rather than the aggregate alone. And the aggregate covers the hourly write policies listed in `AGGREGATE_WRITE_POLICIES` only: the day-windowed ones sit in a different window and are deliberately excluded, so adding a policy means deciding whether it belongs there.
- **An index change is verified by query plan, never by the suite.** `FakeD1` models no indexes at all, so dropping a load-bearing one leaves every test green. Build a scratch database from `migrations/` with `sqlite3`, seed it, `ANALYZE`, then diff `EXPLAIN QUERY PLAN` for every statement in `src/` that touches the table, before and after — the planner is the same engine D1 runs. Migration 0028 dropped eight indexes that way: six were named by no plan, and the two that were fell back to an equivalent seek on the index SQLite already maintains for a `UNIQUE` constraint. Confirm the survivors too. `EXPLAIN QUERY PLAN` also runs against the real database through `wrangler d1 execute --remote`, which is worth doing for anything on the authentication path.
- **Widget reload cadence is per device, not per account, and it is a budget rather than a floor.** Apple budgets WidgetKit reloads per *widget instance* — 40-70 a day for one someone views often — and counts pushes against the same allowance as the widget's own periodic refreshes. A push, though, is not addressed to an instance: `pushTokenDidChange(_:widgets:)` hands back one token covering every widget the extension hosts, and the payload is `aps.content-changed: true`, which reloads all of their timelines together. So one claim spends one reload out of *every placed widget's* budget, and adding a placement costs more allowance without buying more reach. That is why `widget_push_cadence` is keyed by push token — the token is the unit the server can actually ration — and a claim checks two things: at least `WIDGET_PUSH_MIN_SPACING_SECONDS` since that token's last push, and at least one push left in a token bucket that refills one per `WIDGET_PUSH_REFILL_SECONDS` up to `WIDGET_PUSH_BURST`. Both live in one conditional upsert because the read and the write have to be the same act. A bucket rather than a daily quota on purpose: a quota of forty at five-minute spacing is spent in three hours and twenty minutes and leaves the widget dark for the next twenty, which is worse than the flat interval this replaced. The widget's own timeline (`WidgetRefreshPolicy`) asks for an hour until it can see pushes arriving and four hours once it can, so the budget goes to pushes — which fire because something changed — rather than to polling, which fires regardless. It tells the two apart by comparing how long since the last run against *the interval it asked for*, not against a constant: a run that arrives early was triggered by something else. Comparing against a constant is what makes such a policy oscillate. Before shortening either number, work out what it does to the *total* the widget requests per day: asking for more than the budget does not get more reloads, it just lets iOS choose which to drop.
- **The app's own API key cannot publish, and deleting a card is a publish.** Sign-in mints three credentials: the device token (`read`, `device:register`, `actions:run`) the app authenticates most calls with, the app-only credential (`actions:confirm`, `shares:manage`), and the publisher token (`read`, `publish`, `webhook:manage`) that Settings hands to an agent. `DELETE /v1/cards/:id` needs `publish`, so the delete button on a card's detail screen goes through `AppEnvironment.publisherClient()`, not `apiClient()`. Sample cards skip the server entirely — they are generated on-device into the App Group and were never published — which also keeps them removable by someone who has never signed in. Cards arriving through a share or a guest link belong to another tenant and hide the button rather than offering a delete that could only ever be local.
- **An `indexingKey` binding beats `attributeSet`, and no test on this machine can see it.** `@Property(title:indexingKey:)` behaves differently in the two processes that ask. In-process, `defaultAttributeSet` ignores the bindings entirely — bind all of them and it still comes back carrying only `title`, which is derived from `displayRepresentation` rather than from a key — so `attributeSet` must set every attribute by hand or the index gets nothing. But the bindings are *also* compiled into the app's App Intents metadata as `spotlightAttributeKey`, and at index time the system applies them **over** whatever `attributeSet` built. Binding `detail` to `\.contentDescription` therefore replaced a card's value with its subtitle in every Spotlight row — "Water heater · On schedule" instead of the temperature — while the whole unit suite stayed green, because a test can only observe the in-process value. Two builds shipped "fixing" it before the cause was found. Only bind a property whose value is exactly what the attribute should hold; verify a change by reading `Metadata.appintents/extract.actionsdata` out of the built `.app` and checking which properties carry a `spotlightAttributeKey`, never by running the tests.
- **One policy decides what leaves the app for a system surface, and the app alone donates it.** `SpotlightIndex.indexable` is the single gate on what reaches Spotlight *and* what Siri will name or answer for — samples, guest-link cards and shared cards never go, because the SAMPLE badge cannot follow a card into a system index and another tenant's consent can be revoked out from under one. `CardCache.save` is called from both timeline providers as well as the app, so donating from the extension would re-index on every push: `SpotlightIndex` lives in `Sources/App` and is never compiled into `Sources/Widgets`. `donate`/`removeAll` also refresh Siri's parameter list — `ZeroZeroWidgetShortcuts.updateAppShortcutParameters()` is called there, at the one choke point, rather than at the eight call sites. `CardStatusIntent` re-reads the card by id at `perform()` time instead of trusting the `DashboardCardEntity` Siri resolved, because that entity is a snapshot from the last donation and a spoken number quietly an hour old is indistinguishable from a right one; when the id has gone it says so rather than reporting the stale value. Verify Siri phrases **on a device** — this is the same AppIntents rehydration the Simulator does not perform for widget configurations. The app is also the only thing that donates, so the index goes stale whenever a push refreshes `CardCache` with the app closed; `IndexedEntityQuery` (iOS 27, behind the SDK gate) is the one path that repairs it without a launch, and it routes through `indexable` like everything else — an id the system asks about that this app will not index is *removed*, not skipped, or a repair request would reinstate what the policy exists to keep out.
- **The widget update stamp is inferred, and one half of the inference lives in the app.** `WidgetRefreshPolicy.decide` already compares how long since the last run against *what that run asked for* to choose a cadence; the stamp reuses the same `wokenEarly` fact for its colour. Early plus a recent `SharedSettings.markAppWidgetReload()` marker reads as an app-requested reload, early without one reads as a push, on schedule reads as a poll, and a failed in-widget fetch overrides all three as offline. So every `WidgetCenter.reload*` call site in the app has to stamp the marker *before* asking — the extension can run before the call returns — or its reload is misreported as a push. The whole thing is behind `SharedSettings.showWidgetTimestamps`, off by default and reachable only by tapping the version number in Settings.
- **A chart's published limit and its drawn limit are different numbers, and the renderer owns the second.** A producer may send up to `FieldLimits.chartPointCount` (60) points; the wide surfaces draw all of them and the narrow ones cannot — 60 points across a Lock Screen accessory is a 2.8pt step against a 1.5pt stroke, which is a band rather than a trend. So `SparklineView` takes a `maxPoints:` set per call site the way `lineWidth` already is (32 small widget, 24 accessory, 16-24 grid cell by style; everything else uncapped), and `DashboardChart.downsampled(toAtMost:)` averages into that many evenly spaced buckets. Averaging rather than sampling is deliberate and the comment on it explains why: a stride's output depends on which phase it lands on, and LTTB keeps real points at irregular indices that a renderer spacing points evenly then draws at the wrong place in the window. Two things a new chart surface has to get right. Every piece of drawn geometry must read from the downsampled chart, never the original — an unpinned axis derives its bounds from the points, so mixing the two puts the reference rule and the zero line where the plotted values were not scaled against. And the accessibility label deliberately reads the *full* series, because the cap is about how much room a surface has and VoiceOver has the same room everywhere. The guest page needs no cap: its plot is 376px wide, so 60 points is a 6.4px step. Swift's `switch`es will not catch a missing cap — a too-dense plot compiles and renders, it just cannot be read.
- **Multi-card producers use batch upsert.** A producer snapshot that yields multiple related cards must call `POST /v1/cards/upsert-batch` once with `{ "cards": [...] }`, not loop over `/v1/cards/upsert`. This preserves one reload decision per snapshot and avoids burning WidgetKit’s daily reload budget. Adding `replacePrefix` makes the batch authoritative for one id namespace, deleting anything under it the snapshot omits — the only way a producer can shrink. Every card in the batch must sit under that prefix, which is what stops a mistyped prefix from clearing a namespace the request has nothing to do with; don't relax that check.
- **The SDK gate is a pattern, not one incident, and it has two shapes.** `systemExtraLargePortrait` is the *declared-but-unavailable* shape: present in both SDKs, marked `@available(iOS, unavailable)` in the older one. `AppIntents.CancellableIntent` is the second shape and reads more innocently — it is annotated `@available(anyAppleOS 26.4, *)`, which says it back-deploys to an OS *older than the submission machine's SDK*, and it is nonetheless **absent from the iOS 26.5 SDK entirely**. Back-deployable availability is not the same claim as being declared where you are compiling, and only the second one decides whether the name resolves. Both shapes need the same compile-time gate. AppIntents carries its own module version, so its gate is `#if canImport(AppIntents, _version: 301)` — observed `-user-module-version`: `300.5.12` (iOS 26.5), `301.0.51.1.102` (iOS 27.0). The general rule when reaching for anything new: read the availability annotation *and* grep the SDK you actually archive with, because a symbol you can name in Xcode 27 and an `@available` that mentions an old OS together prove nothing about the other machine.
- **Two SDKs build this repo, and a symbol can exist in both while being usable in only one.** Development happens against the iOS 27 SDK (Xcode 27 beta); App Store archives are cut on a machine with the iOS 26 SDK. `WidgetFamily.systemExtraLargePortrait` is the worked example: it is declared in *both* SDKs, but the iOS 26 one marks it `@available(iOS, unavailable)`, so simply naming it there fails with `'systemExtraLargePortrait' is unavailable in iOS` — an `#available` check cannot rescue that, because the problem is compile-time, not runtime. Such symbols go behind a **compile-time SDK gate**, centralised in one place so no call site repeats it — `ios/Sources/Widgets/FullPageWidgetFamily.swift` for the WidgetKit family, `ios/Sources/App/Services/SpotlightReindexing.swift` for `IndexedEntityQuery`, each holding the only reference in its target. Gate on the *SDK*, via `#if canImport(WidgetKit, _version: 749)`, not on the compiler via `#if compiler(>=6.4)`: both distinguish today's two Xcodes, but only the SDK decides whether the symbol is available, and a point release pairing a new Swift with a 26.x SDK would switch a compiler check on and break the submission machine — the one failure the gate exists to prevent. Observed WidgetKit `-user-module-version`: `664.5.28.100` (iOS 26.5), `749.0.1` (iOS 27.0); read it with `head -3` on the SDK's `WidgetKit.swiftinterface`. Keep the runtime `#available(iOS 27.0, *)` *inside* the gate as well — the app deploys back to iOS 26, where offering the family would be a lie. A gate that is silently always-false compiles just as cleanly as a correct one, so prove it toggles by planting a temporary `#error` inside it and building under both Xcodes; verified that way for this one.

## Adding things

- **New widget kind:** add a `*.swift` in `ios/Sources/Widgets/`, register it in `WidgetBundle.swift`, and (if it should appear in the bundle from `WidgetCenter.reloadTimelines`) add its kind string to `Constants.WidgetKinds.all`.
- **New endpoint:** add the handler module in `server/src/`, wire a route in `server/src/index.ts`, add a zod schema in `types.ts`, add a test file in `server/test/`. If iOS needs to call it, add a method to `ios/Sources/App/Services/APIClient.swift`.
- **New field on a response an MCP tool also returns:** add it to that tool's `outputSchema` in the same change. Omitting it does not degrade the tool, it breaks it outright.
- **A security check with nothing to check against must close, not vanish.** `if (expected && actual !== expected)` reads as a check and behaves as an absence when `expected` is unset — that is how an unset `APNS_BUNDLE_ID` made every transaction on the App Store verifiable. The patterns to copy are the environment check beside it, which defaults to `"Production"` and always applies, and `isSecureAdminSecret`, which closes web sign-in rather than opening it. Where an empty value really is meant to be permissive, say so where it is read.
- **Every value signed with `SESSION_SECRET` carries a purpose tag.** `web-session-v1`, `mcp-client-v1`, `mcp-code-v1` — all three are `<payload>.<hmac>` under one key, and an untagged one is what a fourth use would collide with. A new signed value gets its own tag, and a rename gets a compatibility window rather than logging everyone out.
- **Rate limits are keyed on `cf-connecting-ip`, never `x-forwarded-for`.** Cloudflare sets the first and a caller cannot forge it; the second is caller-controlled, so any fallback to it lets a caller pick its own bucket and turns a limit into no limit. Fall back to a single shared `"unknown"` instead, which fails in the safe direction.
- **A route capture is decoded exactly once, by `pathParam` in `index.ts`.** Handlers receive a decoded value. Decoding again corrupts an id containing a literal `%` and throws `URIError` on a malformed escape, which the router turns into a 500 — so the row an operator most wants to delete becomes the one the dashboard cannot delete. There is deliberately no `dec` helper any more.
- **One address, one tenant, and `INSERT OR IGNORE` hides the difference.** `owner_email` is an identity, not a label: a first Apple sign-in resolves against it and an unaccepted share is matched on it, so two tenants sharing an address made sign-in pick one silently and let the other accept shares meant for the first. `tenants_by_owner_email_unique` (migration 0031) closes that — partial, so a disabled tenant releases its address, and on `lower()` because every read already lower-cases. The trap is that both creation paths insert with `OR IGNORE`, which swallows a unique-address conflict exactly as quietly as a repeated id: no row, `changes = 0`, and the caller carries on to hang an `api_keys` row off a tenant that does not exist — a credential shown once that fails its first `requireAuth`. Both paths now read `changes` and throw `TenantEmailTakenError`; `FakeD1` models the constraint so that path is testable at all.
- **New or dropped index:** justify it in the migration by what it does to *rows written*, not to read latency, and verify with an `EXPLAIN QUERY PLAN` diff against a scratch database built from `migrations/`. The suite cannot see indexes.
- **New template type:** extend `DashboardTemplate` in **both** `DashboardCard.swift` and `types.ts`, then add a render path in *every* renderer — `CardView.swift` (app, all widget families, and the Lock Screen accessories), `TVDashboardView.swift`, and the inline script in `server/src/guestPage.ts`, which is what a shared link shows in a browser. The Swift `switch`es fail the build when you miss one; the guest page silently renders an empty card. Update `docs/llms.md`.
- **New cross-cutting request rule:** wire it into **both** the `authed` wrapper in `server/src/index.ts` and the tool dispatcher in `server/src/mcp.ts`. MCP calls handlers directly and inherits nothing from `authed`.
- **New MCP tool:** add an entry to `TOOLS` in `server/src/mcp.ts` — name, description, the zod schema the equivalent route validates with, its required scope, and an `invoke` that calls that route's handler. Nothing else: `tools/list` and the JSON Schema come from the entry. Its `outputSchema` must describe *everything* the handler returns, including fields only present under a flag — see the lockstep bullet above, and add the tool to the drift sweep in `test/mcp.test.ts`. Mention it in the MCP section of `docs/llms.md`.
- **New detail screen showing a payload:** use `RawPayloadDisclosure(payload:endpoint:)` rather than writing the "Raw JSON"/"Example curl" pair again. It owns the encoder, the shell quoting, and the developer-flag check, so a new screen cannot ship its payload to everyone by forgetting the gate — which is exactly how the Live Activity screen did, when the block was a copy of the card screen's and only one copy was edited.
- **New API that exists only in a newer SDK:** put every reference behind one
  centralised compile-time SDK gate rather than sprinkling `#if` at call sites,
  gate on the SDK's module version rather than the compiler version, and prove
  the gate toggles with a temporary `#error` under both Xcodes. See the
  two-SDK bullet in "Things to watch".
- **New Siri shortcut:** add the intent alongside the two in `ios/Sources/App/Intents/DashboardShortcuts.swift` and an `AppShortcut` to `ZeroZeroWidgetShortcuts`. Every phrase must interpolate `\(.applicationName)`; a phrase taking a card needs `parameterPresentation` and a query conforming to `EntityStringQuery`, or Siri has no way to bind what it heard to an id. Keep the wording itself in a pure function next to `CardStatusReport` so it is testable without the AppIntents runtime, and confirm the shortcut reached the build by reading `autoShortcuts` out of the app bundle's `Metadata.appintents/extract.actionsdata`.
- **New Live Activity kind:** extend `LiveActivityKind` in both languages, and update the icon mapping inside `LiveActivityWidget.swift`.

## Quality bar

- **Samples, examples, and docs are written in English.** This repo is public and the sample deck ships inside the app, so a demo string in the author's own language reads as a bug to every other reader. Applies to `examples/*.sh`, `SampleDataFactory`, `docs/`, and any placeholder text a screenshot will capture. Real producer data is whatever language its producer speaks — this is about what we ship as demonstration.
- Code under both `ios/` and `server/` should compile/typecheck without warnings on Xcode 16 / TypeScript 5.6.
- Backend: every endpoint has a zod schema and at least one test (positive and negative path).
- iOS: prefer extending `Sources/Shared/` over duplicating models or rendering between the app and widget targets.
- Don't introduce a new framework dependency on either side without a clear reason — the Worker hand-rolls its router specifically to stay framework-free.
- Comments: only when the *why* isn't obvious. The APNs verification date and the App Group/Keychain invariants are the kinds of comments worth keeping.

## Commit messages

- Use a concise imperative subject that says what the change accomplishes. Do
  not end it with a period.
- Except for genuinely trivial changes, include a body that explains the
  problem or motivation, the chosen approach, and any non-obvious behavior,
  tradeoffs, or invariants. Record relevant verification. Do not merely repeat
  the diff or list the files changed.
- Wrap body text at roughly 72 characters and keep separate ideas in separate
  paragraphs so the message remains useful in `git log` years later.
- Every commit materially assisted by Codex must end with exactly this trailer:
  `Assisted-by: Codex <codex@openai.com>`. Other agents must use an equivalent
  `Assisted-by:` trailer with their own stable identity. Do not use
  `Co-authored-by:` when the agent assisted rather than owned authorship, and do
  not add an assistance trailer to work authored solely by a human.
